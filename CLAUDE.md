# CLAUDE.md

Бекенд підтримки: приймає звернення з хелпдеску, генерує чернетку відповіді через LLM і базу знань, оператор її модерує, підтверджена відповідь іде клієнту.

- Умова завдання: [docs/SPEC.md](docs/SPEC.md)
- Етапи, статус і рішення: [docs/PLAN.md](docs/PLAN.md)

## Команди

Усе запускається в Docker, локальний Python не потрібен.

```bash
docker compose up --build                                # весь сервіс
docker compose run --rm test                             # тести, код монтується в контейнер
docker compose build test                                # після зміни залежностей
docker compose run --rm test ruff check .                # лінтер
docker compose run --rm test ruff format --check .       # форматування
docker compose run --rm test mypy app mock_helpdesk      # типи
docker compose run --rm test alembic revision --autogenerate -m "опис"   # міграція
```

## Архітектура

- `app/main.py`: збирання FastAPI-застосунку, `/health`.
- `app/webhooks.py`: вебхук хелпдеску.
- `app/models.py`, `app/tickets.py`: модель звернення і SQL до неї.
- `app/worker.py`: окремий процес, що генерує чернетки й надсилає відповіді.
- `app/llm/`: замінний інтерфейс LLM-провайдера.
- `mock_helpdesk/`: мок зовнішнього хелпдеску, окремий контейнер.
- `migrations/`: Alembic, єдине джерело схеми БД.

Черга живе в Postgres. Redis і брокер не додавати: вони не потрібні при цьому навантаженні, а Postgres уже є джерелом правди.

Статуси звернення: `received → generating → pending_review → approved → sending → sent`, а також `rejected`, `draft_failed`, `send_failed`, `delivery_unknown`.

## Інваріанти надійності

Порушення будь-якого з них вважається багом, навіть якщо тести зелені.

1. **Вебхук не робить нічого повільного.** Лише валідація і запис у БД. Відповідь за 2 с навіть під піком, жодних викликів LLM чи HTTP у запиті.
2. **2xx лише після коміту.** Якщо БД недоступна, повертаємо 5xx, і хелпдеск повторить доставку.
3. **Дедуплікація робить БД, а не код.** `UNIQUE(event_id)` + `ON CONFLICT DO NOTHING`. Дублікат теж отримує 2xx. Перевірка «SELECT, потім INSERT» заборонена, бо це гонка.
4. **Переходи статусів атомарні.** `UPDATE ... WHERE id = :id AND status = :expected` з перевіркою кількості змінених рядків. Так подвійний клік чи двоє операторів дають один перехід.
5. **Жодних мережевих викликів усередині відкритої транзакції.** Схема завдання: коротка транзакція з `FOR UPDATE SKIP LOCKED` і lease, коміт, виклик, окрема транзакція з результатом.
6. **Завдання не губляться.** У кожного є lease (`locked_until`). Те, що покинув упалий воркер, підбирається наново.
7. **Клієнт не отримує відповідь двічі.** Статус `sending` комітиться до HTTP-запиту. Після 5xx або помилки з'єднання можна повторити автоматично. Після таймауту читання чи простроченого `sending` результат невідомий, тому лише `delivery_unknown` і рішення оператора, без автоповтору.
8. **Ліміт 60 запитів на хвилину діє на весь сервіс.** Усі виклики LLM, зокрема повтори й режим без ключа, проходять спільний лімітер у Postgres. Лімітер у пам'яті процесу заборонений.
9. **Повтори лише для тимчасових помилок.** Обмежена кількість, експоненційний backoff із jitter, лічильник спроб у БД, повага до `Retry-After`. Вичерпані спроби ведуть у видимий оператору статус, а не в тихе зникнення.
10. **У кожного мережевого виклику є явний таймаут.**
11. **Схема змінюється лише міграціями Alembic.** `create_all` заборонений, застосовану міграцію не редагують.
12. **Обмеження живуть у БД.** `NOT NULL`, `UNIQUE`, `CHECK` на статус. Код не єдина лінія оборони.

## Безпека

- Секрети лише в змінних середовища, у коді як `SecretStr`. `.env` не комітиться. Секрети не потрапляють у логи, повідомлення про помилки і відповіді API.
- `reply_url` приходить ззовні, це SSRF. Перед запитом перевіряємо схему і allowlist хостів, `follow_redirects=False`.
- Текст звернення є недовіреним вводом і можливою prompt injection. Передаємо його моделі як дані в окремому блоці. Моделі не даємо жодних інструментів.
- Вивід LLM теж недовірений. Парсимо і валідуємо за схемою, ID статей перетинаємо зі знайденими, URL будує сервер. Без `|safe` у шаблонах, автоекранування Jinja залишається ввімкненим.
- Нічого не йде клієнту без явного підтвердження оператора. Жодного обхідного шляху.
- SQL лише через параметри, без f-рядків.
- Пошта й текст звернення не логуються. У логах лише `ticket_id` і `event_id`.
- Контейнери працюють не від root, порт Postgres назовні не відкрито. Залежності зафіксовані в `uv.lock`.

## Python

- Python 3.12, анотації типів скрізь, `mypy --strict` і `ruff` чисті. `Any` і `# type: ignore` лише з конкретною причиною.
- **Без docstring і пояснювальних коментарів.** Код має читатися сам: зрозумілі імена, малі функції. Коментар лише там, де неочевидно *чому*, наприклад незвичний інваріант чи обхід чужого бага.
- Pydantic на межах системи (HTTP, env, вивід LLM), `dataclass(frozen=True, slots=True)` усередині.
- Налаштування лише через `app.config.Settings`, без `os.environ` по коду.
- Роутери тонкі, логіка в сервісних функціях, SQL зібраний в одному місці для кожної сутності.
- Залежності передаємо явно (клієнт, сесія, `sleep`, генератор випадкових чисел), щоб їх можна було підмінити в тестах. Жодного глобального змінюваного стану.
- Час лише timezone-aware в UTC, у БД `timestamptz`.
- Ловимо конкретні винятки. `except Exception` лише на верхній межі циклу воркера, з логуванням. Виняток не ковтається мовчки.

### Async

- Жодних блокуючих викликів в event loop.
- Фонові задачі через `TaskGroup` або зі збереженим посиланням, ніколи не «запустив і забув».
- `CancelledError` не ковтати. Паралелізм обмежуємо явно через `Semaphore`.
- Воркер коректно завершується за SIGTERM: нових завдань не бере, а незавершене повернеться через lease.

## LLM

- Бізнес-логіка знає лише `LLMProvider`, `LLMRequest`, `LLMResponse` і винятки з `app/llm/base.py`. Усе специфічне для провайдера лишається в `app/llm/`.
- Новий OpenAI-сумісний провайдер додається записом у `PROVIDERS` в `app/llm/factory.py`, несумісний окремим класом-адаптером там само. Перемикання між ними лише через env, без змін поза `app/llm/`.
- Без ключа `KeylessProvider` усе одно робить справжній запит, ігнорує його результат і повертає статичну відповідь із затримкою 5–30 с. Решта системи не розрізняє ці режими.
- Адаптер не повторює запити сам, він лише класифікує помилку на `LLMRetryableError` і `LLMPermanentError`. Повтори належать воркеру.

## Тести

- Перевіряємо поведінку й інваріанти, а не деталі реалізації. Кожен інваріант вище має свій тест.
- Гонки, дедуплікацію і чергу тестуємо на справжньому Postgres. SQLite і моки БД заборонені.
- Зовнішній HTTP замінюємо через `httpx.MockTransport`. Реальних викликів LLM у тестах немає, реальних затримок теж: `sleep` підміняється.
- Виправлення бага починається з тесту, що його відтворює.
