# Support drafts

Бекенд підтримки. Хелпдеск надсилає звернення на вебхук, сервіс шукає статті в базі знань і генерує через LLM чернетку відповіді з посиланнями. Оператор підтверджує або відхиляє чернетку, і підтверджена відповідь іде клієнту через API хелпдеску. Умова завдання: [docs/SPEC.md](docs/SPEC.md).

Стек: Python 3.12, FastAPI, PostgreSQL 16, SQLAlchemy 2 (async), Alembic, Jinja2, Docker Compose. LLM підключається через замінний інтерфейс: Groq, Gemini, OpenRouter, OpenAI або будь-який OpenAI-сумісний API.

## Розгорнутий сервіс

| Що | Адреса |
|---|---|
| Вебхук | `POST https://13-49-142-32.sslip.io/webhooks/helpdesk` |
| Інтерфейс оператора | https://13-49-142-32.sslip.io/tickets (Basic Auth: `operator` / `NObDqcu2IyFH0oHB`) |
| Health | https://13-49-142-32.sslip.io/health |
| База знань | https://13-49-142-32.sslip.io/kb |
| Мок хелпдеску | https://mock.13-49-142-32.sslip.io |

Деплой: AWS EC2 `t3.micro`, Caddy з HTTPS від Let's Encrypt. Кожен push у `main` після зелених тестів автоматично деплоїться через GitHub Actions.

Модель на деплої: Groq `openai/gpt-oss-120b` на безкоштовному тарифі. Цей тариф пік з умови не витримує, деталі в розділі [Ліміти LLM і пік навантаження](#ліміти-llm-і-пік-навантаження).

Найпростіше перевірити так:
1. Відкрийте мок і створіть звернення формою «Нове звернення». Галочка «надіслати двічі» перевіряє дедуплікацію.
2. За кілька секунд звернення з чернеткою з'явиться в інтерфейсі оператора.
3. Підтвердіть чернетку, і відповідь з'явиться в журналі мока.

Щоб надіслати звернення на вебхук напряму, вкажіть у `reply_url` внутрішню адресу мока. Відповіді йдуть лише на хости з allowlist (див. [Безпека](#безпека)):

```bash
curl -X POST https://13-49-142-32.sslip.io/webhooks/helpdesk \
  -H 'Content-Type: application/json' \
  -d '{"event_id":"evt_demo_1","ticket_id":"T-1042","customer_email":"user@example.com","message":"Не можу експортувати звіт у PDF","reply_url":"http://mock-helpdesk:8001/tickets/T-1042/replies"}'
```

## Локальний запуск

Потрібен лише Docker з Compose 2.24 або новішим.

```bash
git clone https://github.com/Gandalff2k/TestTask02.git
cd TestTask02
docker compose up --build
```

Файл `.env` не потрібен: без нього сервіс працює в режимі без API-ключа (див. нижче). Перший запуск триває 1–2 хвилини: збірка образу, міграції БД, завантаження бази знань.

| Що | Адреса |
|---|---|
| Інтерфейс оператора | http://localhost:8000/tickets (без пароля, поки не задано `OPERATOR_PASSWORD`) |
| Вебхук | `POST http://localhost:8000/webhooks/helpdesk` |
| Health | http://localhost:8000/health |
| База знань | http://localhost:8000/kb |
| Мок хелпдеску | http://localhost:8001 |

Надіслати звернення з консолі:

```bash
curl -X POST http://localhost:8000/webhooks/helpdesk \
  -H 'Content-Type: application/json' \
  -d '{"event_id":"evt_8f2a","ticket_id":"T-1042","customer_email":"user@example.com","message":"Не можу експортувати звіт у PDF","reply_url":"http://mock-helpdesk:8001/tickets/T-1042/replies"}'
```

У Windows PowerShell зручніше скористатися формою мока: curl з кирилицею в аргументі може надіслати текст не в UTF-8.

### Режим без API-ключа

Якщо `LLM_API_KEY` порожній, сервіс усе одно робить справжній запит до провайдера (отримує 401), ігнорує результат і за 5–30 с повертає статичну відповідь. Ця відповідь у тому самому JSON-форматі, що й від моделі, і далі проходить той самий парсер, лімітер і чергу, що й реальна. Посилання в чернетці беруться зі знайдених статей.

### Підключення LLM

Скопіюйте `.env.example` у `.env` і задайте провайдера:

```bash
cp .env.example .env
```

```dotenv
LLM_PROVIDER=groq
LLM_API_KEY=gsk_...
LLM_RATE_LIMIT_PER_MINUTE=60
```

| `LLM_PROVIDER` | Модель за замовчуванням | Що задати |
|---|---|---|
| `groq` | `openai/gpt-oss-20b` | `LLM_API_KEY` |
| `gemini` | `gemini-3.8-flash` | `LLM_API_KEY` |
| `openrouter`, `openai` | немає | `LLM_API_KEY`, `LLM_MODEL` |
| `custom` | немає | `LLM_BASE_URL`, `LLM_MODEL`, за потреби `LLM_API_KEY`. Наприклад, Ollama: `http://host.docker.internal:11434/v1` |

`LLM_RATE_LIMIT_PER_MINUTE` — спільний ліміт на весь сервіс, за замовчуванням 60, як в умові. Його варто виставити під ліміти свого ключа (див. наступний розділ). Після зміни `.env` перезапустіть стек: `docker compose up -d`.

### Ліміти LLM і пік навантаження

Пік з умови — 500 звернень за 10 хвилин, тобто близько 50 викликів LLM на хвилину. Один виклик з трьома статтями займає 1,3–1,6 тис. токенів, тож потрібно приблизно 75 тис. токенів на хвилину.

- **Сервіс** розрахований на 60 запитів на хвилину. Прогін 500 подій за 10 хвилин у режимі без ключа: генерація встигала за потоком, жодної втрати (результати нижче).
- **Безкоштовний Groq**, на якому працює деплой, дає 8 тис. токенів на хвилину і 1000 запитів на добу. Цього вистачає на 5–6 звернень на хвилину, тому на деплої стоїть `LLM_RATE_LIMIT_PER_MINUTE=6`. Під піком вебхук, як і раніше, приймає все за мілісекунди, а черга чернеток розбирається поступово. Нічого не губиться, просто довше.
- **Платний ключ** (наприклад, Groq Developer: 250 тис. токенів і 1000 запитів на хвилину) тягне пік без змін у коді: потрібні лише `LLM_API_KEY` і `LLM_RATE_LIMIT_PER_MINUTE=60`.
- **Якщо ліміт задано вищим, ніж дозволяє ключ**, сервіс підлаштовується сам. На 429 від провайдера весь сервіс робить паузу на `Retry-After`, а звернення повертається в чергу без втрати спроби. Перевірено на реальному ключі: 25 звернень одночасно при завищеному ліміті дали 42 відповіді 429, але всі 25 отримали чернетку за 101 с.

## Як це працює

```
хелпдеск ──POST /webhooks/helpdesk──▶ api ──INSERT──▶ PostgreSQL ◀── worker ──▶ LLM
                                        │                 ▲            │
оператор ──/tickets (Jinja2)────────────┘                 │            └──POST reply_url──▶ хелпдеск
                                                          └── черги, lease, лімітер
```

- **`api`**: вебхук, інтерфейс оператора, сторінки бази знань, `/health`.
- **`worker`**: дві черги в одному процесі. Генерація чернеток іде до 30 паралельно, надсилання відповідей до 5.
- **`migrate`**: міграції Alembic і синхронізація статей з `kb/*.md` при кожному старті.
- **`mock-helpdesk`**: мок хелпдеску з керованими відмовами, журналом відповідей і формою створення звернень.

Черги, лімітер і стан звернень живуть у Postgres. Redis і брокер не потрібні: при такому навантаженні Postgres уже є джерелом правди.

Статуси звернення:

```
received → generating → pending_review → approved → sending → sent
                │              │                       │
                ▼              ▼                       ├─▶ send_failed
          draft_failed      rejected                   └─▶ delivery_unknown
```

### База знань і пошук

8 статей про вигаданий сервіс звітів «Звітник» лежать у `kb/*.md` і згенеровані AI. Пошук іде через `pg_trgm`, оцінка — середнє `word_similarity` по словах запиту. Заголовок і теги важать більше за текст, стоп-слова й короткі слова відкидаються. Так ловляться словоформи («експортувати звіт» → «Експорт звіту») без стемера, якого для української в Postgres немає.

Модель повертає лише ID використаних статей. Сервер перетинає їх зі знайденими й сам будує абсолютні URL, тож вигадане посилання в чернетку не потрапить. Якщо статей не знайдено, чернетка все одно генерується, а оператор бачить попередження.

## Надійність

| Вимога з умови | Як виконано |
|---|---|
| Хелпдеск чекає ≤ 2 с | Вебхук лише валідує і пише в БД з дедлайном 1,5 с. Якщо БД недоступна або зависла, за 1,5 с приходить 503, і хелпдеск повторює доставку. 2xx повертається лише після коміту |
| Дублікати, зокрема одночасні | `UNIQUE(event_id)` + `INSERT ... ON CONFLICT DO NOTHING`. Дублікат теж отримує 200 |
| Звернення не можна втрачати | Звернення зберігається до відповіді. Зламаний Unicode і NUL вирізаються, а не дають 5xx. Черги в Postgres з lease: упалий воркер не губить звернення, його підхопить інший |
| Пік 500 за 10 хв | Async-воркер до 30 одночасних викликів LLM (1 запит/с × до 30 с затримки) |
| 60 запитів на хвилину на весь сервіс | Спільний лімітер у Postgres, 1 слот на 1,05 с для всіх процесів, зокрема повторів і запитів без ключа |
| Хелпдеск повертає 5xx або не відповідає | 5xx, 429 і помилка з'єднання дають повтор з backoff. Таймаут читання дає `delivery_unknown` без автоповтору |
| Клієнт не отримує відповідь двічі | Див. нижче |

**Чому таймаут не повторюється автоматично.** У API хелпдеску немає ключа ідемпотентності, а таймаут не означає, що відповідь не дійшла: хелпдеск міг її прийняти й не встигнути відповісти. Тому:
- статус `sending` комітиться до HTTP-запиту;
- після таймауту або падіння воркера посеред запиту звернення переходить у `delivery_unknown`, і рішення ухвалює оператор («Надіслати ще раз» або «Клієнт отримав»);
- подвійний клік чи двоє операторів дають один перехід (`UPDATE ... WHERE status = ...`).

Мок навмисно імітує сценарій «прийняв, але відповів пізно». У прогоні нижче автоповтор продублював би відповідь 36 клієнтам.

Повна таблиця рішень з причинами: [docs/PLAN.md](docs/PLAN.md#рішення).

### Безпека

- **SSRF через `reply_url`.** Відповіді йдуть лише на хости з `HELPDESK_ALLOWED_HOSTS` (за замовчуванням `mock-helpdesk`), редиректи не виконуються. Хост з прикладу умови `helpdesk.example.com` отримає `send_failed` з поясненням. Щоб надсилати на свій хост, додайте його через кому.
- **Prompt injection.** Текст звернення передається моделі як JSON-дані з явною вказівкою не виконувати з нього інструкцій. Інструментів модель не має, і нічого не йде клієнту без підтвердження оператора.
- **XSS.** Увесь текст клієнта й моделі екранується в шаблонах.
- **Доступ оператора.** Basic Auth вмикається через `OPERATOR_PASSWORD`. POST з чужого `Origin` чи `Sec-Fetch-Site` отримує 403.
- **Секрети.** Лише в `.env`, який не комітиться. У логах немає пошти й тексту звернень. Відповідь 422 не повертає введені дані.

## Тести і перевірки

```bash
docker compose run --rm --build test                                # 208 тестів
docker compose run --rm test ruff check .
docker compose run --rm test ruff format --check .
docker compose run --rm test mypy app mock_helpdesk scripts
```

Тести працюють на справжньому Postgres (окрема БД `support_test`), без реальних викликів LLM і без реальних затримок. Вони покривають:
- гонки дублікатів і подвійних підтверджень;
- недоступну й завислу БД;
- lease і роботу після падіння воркера;
- захист від застарілого власника завдання;
- лімітер на кілька процесів і паузу на 429;
- класифікацію відповідей хелпдеску;
- наскрізне надсилання в мок з відмовами без дублікатів;
- XSS, CSRF, Basic Auth і SSRF-allowlist;
- пошук по базі знань.

CI (`.github/workflows/ci-cd.yml`) на кожен push і PR запускає ці ж перевірки, а push у `main` після зелених тестів деплоїть на сервер.

### Навантажувальний прогін

```bash
docker compose up -d --build
docker compose run --rm test python scripts/load_test.py --approve
docker compose logs worker --no-log-prefix | python scripts/llm_rate.py
```

Скрипт поводиться як хелпдеск:
- чекає відповідь 2 с і повторює доставку при 5xx чи обриві;
- 20 % подій надсилає вдруге через 1–30 с, 5 % трьома одночасними копіями;
- після генерації підтверджує кожну чернетку двома паралельними запитами;
- звіряє журнал мока на дублікати.

Результат: 500 подій за 10 хвилин у режимі без ключа. Під час прогону свідомо ламалися воркер (`kill -9` на 120-й с), Postgres (рестарт на 246-й с) і API (`kill -9` на 357-й с).

| Метрика | Значення |
|---|---|
| Затримка вебхука | p50 19 мс, p99 43 мс, максимум 120 мс |
| Прийнято / у БД / втрачено | 500 / 500 / 0 |
| Падіння API | 26 запитів отримали помилку з'єднання, хелпдеск їх повторив, усі дійшли |
| Генерація | усі 500 чернеток готові через 20 с після останньої події |
| Виклики LLM | не більше 58 за будь-які 60 с |
| Подвійні підтвердження | 500 застосовано, 500 відхилено як повтор |
| Надсилання (мок: 20 % 503, 10 % зависань) | 441 `sent`, 59 `delivery_unknown` |
| Журнал мока | 477 відповідей (441 + 36 «прийняв, але відповів пізно»), 0 дублікатів |

## Деплой на сервер

На свіжому Ubuntu (перевірено на 26.04, `t3.micro`, 20 ГБ диска, відкриті порти 22, 80 і 443):

```bash
curl -fsSL https://raw.githubusercontent.com/Gandalff2k/TestTask02/main/deploy/bootstrap.sh -o bootstrap.sh
bash bootstrap.sh https://github.com/Gandalff2k/TestTask02.git
```

Скрипт створює swap на 2 ГБ, ставить Docker з пакетів Ubuntu, клонує репозиторій у `~/app` і створює `~/app/.env`. У `.env` заповніть ключ LLM, паролі і домени:

```dotenv
APP_HOST=13-49-142-32.sslip.io
MOCK_HOST=mock.13-49-142-32.sslip.io
PUBLIC_BASE_URL=https://13-49-142-32.sslip.io
OPERATOR_PASSWORD=<довгий пароль>
POSTGRES_PASSWORD=<довгий пароль>
```

Далі перелогіньтесь (щоб застосувалась група `docker`) і запустіть:

```bash
bash ~/app/deploy/deploy.sh
```

Скрипт оновлює код до `origin/main`, збирає образ, піднімає стек разом з Caddy (`compose.prod.yaml`) і чекає, поки `api` стане здоровим. HTTPS-сертифікат Caddy отримує сам. `sslip.io` дає домен без реєстрації: `<ip-через-дефіси>.sslip.io` резолвиться в цю IP.

Автодеплой з GitHub Actions потребує секретів репозиторію:
- `DEPLOY_HOST`: IP сервера;
- `DEPLOY_USER`: `ubuntu`;
- `DEPLOY_SSH_KEY`: приватний ключ;
- `DEPLOY_KNOWN_HOSTS`: вивід `ssh-keyscan <ip>`.

## Обмеження

- **Безкоштовний Groq** не тягне пік з умови вчасно (див. вище).
- **Запити англійською** не знаходять українських статей: пошук триграмний, без перекладу. Модель тоді чесно передає питання спеціалісту.
- **Редагування чернетки** оператором немає: умова вимагає лише підтвердити або відхилити.
- **Журнал мока** зберігається в пам'яті й очищується після перезапуску контейнера.
- **HTTPS працює лише за доменом.** Гола IP по HTTP перенаправляється на домен, а по HTTPS не відкриється, бо сертифікат на IP не видається.
